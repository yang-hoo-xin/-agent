# Evidence-Gated Project Directions

This file lists directions to investigate. It does not state that any direction
is currently implemented, tested, deployed, or owned by the user.

For a selected direction, read current source and the smallest relevant test or
receipt before writing it into resume prose. 为什么要有它： the former project
highlight list mixed historical design, possible extensions, and verified
behavior.

## Retrieval

Possible focus: dense or sparse retrieval, fusion, scoring, reranking, and
failure behavior.

Required evidence: current retriever owners, configuration, executed evaluation
or focused tests, and the revision or environment for any metric.

## Ingestion and document lifecycle

Possible focus: loading, splitting, transformation, embedding, indexing,
idempotency, deletion, or recovery.

Required evidence: current pipeline owners and a focused lifecycle result.
Source structure alone does not prove scale, cost reduction, or end-to-end
success.

## Provider and component boundaries

Possible focus: interfaces, factories, configuration-driven selection, and
failure policies.

Required evidence: currently supported providers and a test or run for the
specific switch being claimed. An interface or reserved option does not prove a
working integration.

## MCP surface

Possible focus: protocol transport, tool exposure, structured responses, and
client interaction.

Required evidence: current server metadata and protocol tests. Do not reuse old
tool counts, method names, protocol versions, or client support claims.

## Multimodal handling

Possible focus: image extraction, captioning, storage, retrieval, and response
assembly.

Required evidence: current source plus a focused observed path. Do not claim a
Vision model, retrieval quality, or client rendering without its bound result.

## Observability

Possible focus: trace capture, query or ingestion inspection, dashboards, and
failure diagnosis.

Required evidence: current trace fields, UI owners, and a focused test or trace.
Do not infer page counts or diagnostic coverage from an old design.

## Evaluation

Possible focus: evaluation adapters, datasets, metrics, comparison, and result
lineage.

Required evidence: the exact evaluator, dataset identity, executed result, and
limitations. Do not supply threshold values or quality gains from a template.

## Controlled code delivery

Possible focus: evidence discovery, planning, proposal review, approval-bound
apply, build, runtime evidence, and delivery.

Required evidence: the exact stage and artifact reached by a current bound run.
A successful earlier stage does not prove later stages.

## Engineering verification

Possible focus: focused tests, deterministic validation, reproducible builds, or
failure recovery.

Required evidence: current commands and results. Do not claim historical test
counts, all-green status, development-stage completion, or coverage without a
current authoritative source.

## Agent integration

Possible focus: a verified tool-using workflow or a controlled specialist within
the current graph.

Required evidence: current implemented route and executed behavior. ReAct,
multi-agent, or generic Agent ecosystem narratives are not resume facts merely
because they are technically possible.
