# 评测驱动开发协议

状态：2026-09-29 更新适用范围；原计数口径继续用于已有实验。日常推进见[交付与评测方式](EVALUATION_FIRST_CYCLE.md)，最新证据与缺口见[成果清单](PROJECT_OUTCOMES.md)，本协议本身不证明实现或通过。

目标是随着真实功能开发积累四类证据：完成多少独立任务、相对哪个基线有改善、付出多少成本、失败时是否守住执行边界。简历中的【待测】是证据需求，不是必须得到正向结果的指标承诺。

2026-10-07 已执行一轮跨模块工程验证，逐案例结果、首败、两类缺陷修复与未完成边界见[本轮原件索引](../artifacts/eval_driven_20261007/module-edd-v1/REPORT.md)。稳定选集为 `tests/fixtures/evaluation/module_coverage_v1.json`；`scripts/prepare_module_evaluation.py` 复用既有源码快照，`scripts/run_module_evaluation.py` 执行现有 pytest 并保留逐阶段记录。工程案例、参数变体和重复执行分开计数，不混入独立 Mod 任务分母。为什么要有它：模块专题需要可复查的实际结果，也需要避免把局部契约检查扩大成模型或产品交付能力。

相关历史接线证据可参考[复用审计](audits/EVALUATION_REUSE_AUDIT_20260926.md)，当前实现以任务所需源码、配置和调用者为准；产品执行边界见[产品契约](ACTIVE_PRODUCT_CONTRACT.md)。每次实验的详细事实保留在其原始记录中，活动摘要只引用。为什么要有它：历史审计是导航线索，不是每次开发的必读阶段；同一数字不能在多份摘要中各自漂移。

## 1. 按所需结论复用入口

| 需要回答的问题 | 现有入口 | 使用范围 |
| --- | --- | --- |
| 正常任务是否完成、策略是否值得采用 | `run-request`、`scripts/run_product_trial_batch.py`、原delivery adapter | 实际验收/Apply/Build及适用运行；配对仍需绑定任务、身份和预算 |
| 同一失败候选能否修好 | `scripts/run_patch_sft_eval.py --mode fixed_failure`、共享Patch/Repair与既有C#裁判 | 给定Plan和受控C1的阶段结果，按实际样本适配manifest，保留候选来源 |
| 执行过什么、耗费什么、哪里失败 | `scripts/measure_product_task.py`、`scripts/product_trace.py` | 汇总所选执行段；全任务、跨段、人工和金额字段须另核完整性，未知不补零 |
| 检索、治理、训练策略的专项问题 | `scripts/evaluate.py`、`scripts/run_governance_scenarios.py`、现有Self-RAG训练/推理入口 | 各自语料、故障或样本范围，不能合并进Coding独立任务分母 |
| 改动是否破坏既有行为 | 受影响pytest与`.github/workflows/ci.yml`现有选集 | 普通改动用相关检查，整合/发布检查点运行选定完整范围 |

按任务核对入口与实际输出后复用；新增采集仅补所选结论确实缺少的字段，原模型/工具正文保留一次。为什么要有它：模块存在不是结果已证实，但也不需要为每项指标另建runner、索引或记录系统。

## 2. 每次开发的闭环

日常开发按下表完成一个需求。后续数据集、配对和指标章节是对应实验的参考口径，不是每次修改的前置门禁；纯文档维护只检查受影响内容。为什么要有它：交付一个功能与证明一项统计收益需要不同的工作量，不能让后者阻塞前者。

| 步骤 | 交付物及完成条件 | 为什么要有它 |
| --- | --- | --- |
| 1. 确定需求和验收 | 写清预期行为、保留行为、目标工程与允许副作用；沿入口→配置→工厂→实现→验收检查可复用模块 | 为什么要有它：先找已有接线与可观察结果，避免重复建设或实现后改判定 |
| 2. 调查并实现 | 读取当前绑定源码和所需依赖；能复现的缺陷先保留原反例；一起完成实现所需的相关修改 | 为什么要有它：日常修复允许协调修改多个接缝，单因素限制只适用于声称因果收益的实验 |
| 3. 正常入口验收 | 跑原反例、保留行为与受影响调用者；行为敏感改动并行独立审阅；按任务执行真实构建或运行 | 为什么要有它：辅助函数通过不足以证明用户实际路径可用，重复无关全集也不会补足这个缺口 |
| 4. 应用并交付 | 展示精确差异，消费有效的人审或明确任务委托授权；Apply 前重验当前源码和修改范围，交付工程、补丁与适用验收结果 | 为什么要有它：消除重复审批的同时，仍须把实际写入绑定到具体变更与当前前像 |
| 5. 保留必要结果 | 一份结果索引关联下表记录；遇到工程故障记录首个原因、修复和受影响复验，再继续交付 | 为什么要有它：失败要能定位和回归，重复解释与多份汇总不应成为新的开发任务 |

日常记录只保留能回答以下问题的字段；详细模型和工具正文由现有 Trace 保存一次，汇总引用它。源码哈希、修改范围、授权绑定和真实验收继续由执行入口检查。为什么要有它：减少重复信息供给和报告工作，同时保留成败、成本与越界的判断依据。

| 问题 | 必要记录 | 为什么要有它 |
| --- | --- | --- |
| 做了什么、是否完成 | 原需求、输入版本、最终补丁/工程/产物、验收命令及逐项结果；标明开发者或产品模型生成 | 为什么要有它：交付和归因都要能核对实际产物 |
| 付出多少成本 | 本次执行起止、实际模型调用与 Token、工具调用、开发者介入；未知成本留空 | 为什么要有它：失败尝试也消耗资源，不能只统计最终成功片段 |
| 是否守住边界 | 允许目录、精确 diff、源码前像与 Apply 后校验、授权来源、实际副作用 | 为什么要有它：少做重复门禁不等于放宽修改权限 |
| 为什么停下、怎样恢复 | 首个失败代码与直接输入/输出引用、修复版本、必要复验结果 | 为什么要有它：直接原因能推动修复，重复的限制声明不能替代诊断 |

需要比较基线与改进、报告独立任务成功率或资源收益时，再预注册对应任务集、预算和判定，冻结候选并执行配对/留出。为功能交付协调修改了多个因素时如实记录，之后再隔离因素做收益实验。为什么要有它：完成工程任务与估计策略收益可以顺序推进，无需先证明通用提升才能交付。

### 2.1 单个任务的成功条件

以下是对既有结果的语义映射，不新增运行阶段、审批或必填JSON Schema；任务开始时在已有需求/spec中说明交付范围，旧实验继续按原范围解释。为什么要有它：明确“成功”不需要再建设控制面，也不能事后缩小范围追认旧失败。

必需验收项来自当前需求、接口合同及已授权交付范围；旧任务叙述或模型规划中的推测不自动新增义务。为什么要有它：验收检验用户需要的结果，不能把所有中间猜想重新变成必须先证明的门禁。

| 判定 | 可计成功的条件 | 为什么要有它 |
| --- | --- | --- |
| 补丁可用 `code_ready` | 当前候选可取回且可应用到绑定基线；需求/缺陷验收和必要保留行为检查全部通过，适用编译通过；没有篡改受保护裁判或以放宽断言冒充修复 | 为什么要有它：代码有变化、能编译或部分测试通过，都不足以确认需求已完成。 |
| 任务已交付 `delivered` | 补丁可用，并完成预定交付范围：补丁包、授权Apply、实际Build、适用Runtime等各按本任务要求；测试对象、最终修改与交付产物身份一致，源码/范围/副作用符合授权，遵守本次预算 | 为什么要有它：可审阅补丁与实际应用交付有不同终点；纯补丁任务无需强加部署，要求运行的任务也不能用Build替代。 |
| 自主程度 | 在上述结果之外标记无技术救援、辅助完成或未知；补解法、手改候选、运行中针对失败改提示/增预算另记辅助。必要澄清与批准单列；没有完整介入记录就保留未知 | 为什么要有它：原生模型提案只证明候选来源，不证明全过程无人救援；自主性不是更高一级的验收结果。 |
| 部分进展/未完成 | 保留已通过检查、剩余失败和已到达阶段；只要必需项失败或未知，就不计该任务已交付 | 为什么要有它：部分进展可用于诊断和选路，不能把3/4检查写成75%的任务交付。 |

判定优先使用真实执行和环境终态。诊断是否详细、是否调用指定工具、是否遵循某条推理路径，只在任务确有该约束时评价；代码质量或证据支持度可作补充评分，不能覆盖功能失败。为什么要有它：允许不同正确实现，同时保留用户真正要求的边界。

需求/缺陷检查与保留行为检查按语义分组；公开/私有仅描述反馈可见性，两种分组不能互换。空的检查组标不适用并说明原因；必需行为缺少裁判时保留未验证。建立或校准缺陷评测裁判时，核对原实现失败、已知正确控制通过，所需条件应可由需求、接口合同或允许材料得知；普通缺陷交付按可复现反例及修复后验收推进。为什么要有它：防止遗漏检查被算成满分、错分回归或隐藏偏好，同时不要求每个新缺陷先具备独立参考解才允许开发。

## 3. 数据集与身份

1. 独立任务按 `task_id + task_version + project_revision` 登记，并额外标注项目、语言、任务类型、根因家族和近重复组。同题重复、续接、种子变化、参数替换和同根因小变体不增加独立任务数。统计语言只计实际修改且完成对应验收的源码语言，配置格式单独列。为什么要有它：运行次数、检查点数和技术栈长度都不能冒充泛化覆盖。
2. development 可用于调试；validation 可用于候选选择；holdout 在候选冻结后才由独立评测方释放必要任务输入，答案与私有验收不进入产品模型或实现者的调优上下文。按项目/根因家族/近重复组做隔离；若只在同项目新家族留出，明确称“同项目独立任务”，不称跨项目泛化。为什么要有它：简单随机拆题不能阻止任务解法泄漏。
3. 维护 exposure 记录：何人/哪个模型何时看过题目、源码、根因、参考解和测试；已针对样本调优则转为开发/回归用途并补充新的留出版本。查看公开身份元数据不自动等于看到答案；独立性由访问记录判定。为什么要有它：既不能把公开 metadata 当泄漏，也不能仅凭 heldout 文件名宣称未参与调优。
4. 每次实验冻结平台 commit 与工作区差异/未跟踪执行文件哈希、目标源码快照、语料/索引、模型标识或 digest、模板/采样设置、工具链、依赖、judge 和协议版本。可用不可变快照，不要求为冻结而提交他人 WIP。为什么要有它：当前主树大量未提交修改，单独 HEAD 无法重建实际被执行版本。
5. baseline 与 candidate 共用任务、初始环境、工具权限、反馈可见性、judge 和累计预算；分别从干净目标快照运行，不能共享一次运行形成的记忆/缓存，除非缓存正是冻结的实验因素。交错顺序，记录冷/热缓存和可用的随机种子。为什么要有它：先运行的一臂不能免费给后一臂提供解法，环境漂移也会影响耗时。
6. 预先登记全部任务、重复次数、最大模型调用/Token/时间/金额或本地计算预算和异常处理。预算内模型修订属于同一运行；人工修改提示、补解法、平台热修后另建版本与运行，保留原失败。为什么要有它：防止重试挑最好结果、重领预算或把人工救援记作自主修复。

## 4. 指标字典

每个比率同时报告分子/分母；分母为零写 N/A，缺失写 unknown 并报告覆盖率。没有证据的 null 不填 0。为什么要有它：小样本百分比、零成本和未知值容易造成错误印象。

### 4.1 端到端交付与迭代

| 指标 | 统计口径 | 为什么要有它 |
| --- | --- | --- |
| 项目/语言/任务类型数 | 分别报告计划、已尝试、已成功覆盖的去重数量及清单；类型在运行前分类 | 为什么要有它：准备了多项目不代表交付了多项目，事后拆分类会扩大覆盖 |
| 首轮独立任务交付率 | 首个预注册完整trial中达到上述delivered条件的独立任务数 / 预注册交付任务数N；一个trial可含工具调用、初次提交、反馈、预算内自动修订和授权续接 | 为什么要有它：首轮完整运行成功不等于一次模型生成成功，也不能选第一个成功的运行作为首轮 |
| 首次补丁提交通过 | 未经修订的首个Patch提交达到code_ready的任务数 / 预注册任务数N；工具请求不是补丁提交，格式无效的首个提交不能跳过，无候选/未知分别列出且不计成功 | 为什么要有它：把初稿能力与收到反馈后的修复能力分开，避免只统计成功进入裁判的候选 |
| 补丁到交付的落差 | 同一任务表中分别列code_ready数、delivered数，以及待批准/Build失败/Runtime未验等原因 | 为什么要有它：准确定位交付末端的问题，不把阶段通过直接提升为完整任务成功 |
| 未完成分布 | 分开报告模型/行为失败、边界阻断、预算耗尽、基础设施失败、未执行及验收未知；全部仍在预注册分母 | 为什么要有它：剔除困难/未启动任务会抬高完成率；正确阻断也不等于完成修改 |
| 自主与辅助完成 | 主指标为无人工技术介入的完成；人工提示根因、编辑补丁、调预算等归辅助完成，另列总交付 | 为什么要有它：人工救援成功不能被归到 Agent 自主能力 |
| 修复成功率 | 同一版本及预算内，首次验收失败后自主修订并最终通过的运行数 / 首次验收失败且协议预先允许修订的运行数；无余额仍计入分母。各臂进入该阶段的样本不同则仅作条件性描述；比较修订机制另固定同一C1、源码和反馈 | 为什么要有它：既防止漏掉失败成本，也避免把不同的进入样本当作严格配对能力比较 |
| 人工介入 | 按事件分别记录需求澄清、必要批准、技术救援、环境恢复，给出每任务次数 | 为什么要有它：必须批准与提示答案对自主性的意义不同 |
| 基线变化 | 同一独立任务集的绝对成功数、百分点差、每任务配对胜/平/负；跨版本变化和单因素消融分开命名 | 为什么要有它：多个模块一起变好时，不能把增益全归于某一策略 |
| 重复运行波动 | 首次运行主表保留；另报每轮成功数、均值/范围和每任务成功频次；建议探索阶段 3 次，不把重复计成新任务 | 为什么要有它：一次偶然通过和稳定交付不同，三次也不构成充分统计显著性 |
| 重复可靠性 | 对预定N题各k次，分别报观察到至少一次交付的题数/N、所有k次均交付的题数/N、成功运行数/(N×k)；缺失/超时留在预定清单并单列 | 为什么要有它：碰到一次成功与每次都可靠是不同能力，不用平均成功率的幂冒充实测稳定性 |
| 既有行为回归 | 同版本验收中的保留行为失败数 / 实际执行保留检查数，附受影响任务；工程 pytest 另列 | 为什么要有它：产品行为验收与平台单测覆盖不同主张 |

无改动正确、需求缺失时正确停机等任务单列“决策正确率”，不混入交付任务完成率；有意注入拒绝条件的治理任务也单列。为什么要有它：安全地拒绝是能力，但不能用拒绝案例提高交付成功数。

基础设施/裁判故障单列直接原因，主交付分母保持预定任务清单；若另报有效环境下的条件结果，明确该子集及排除原因。观察不到成功不等于已证明代码错误。为什么要有它：既不掩盖产品未完成，也不把环境问题全部归因于模型。

### 4.2 检索与回答

| 指标 | 统计口径 | 为什么要有它 |
| --- | --- | --- |
| 规模 | 文档/文件数、去重内容量、chunk 数、索引版本与独立题数；按文档问答和活源代码导航分表 | 为什么要有它：RFC 问答优势不能直接推广成代码 Agent 收益 |
| Evidence Recall@K | 每题前 K 命中的去重相关证据单元数 / 人工核验的相关证据单元总数，然后宏平均；固定 K，记录证据 span 与版本 | 为什么要有它：大量重复 chunk 和只标一个容易命中的证据都会扭曲召回 |
| 引用正确率 | 实际引用中，来源有效且蕴含所关联事实的引用数 / 全部实际引用数；无引用为 N/A；另报需证据事实的引用覆盖率 | 为什么要有它：不引用或只引用一句容易支持的话，不能获得虚假的高可信度 |
| 正确拒答率 | 预先标为不可回答的题中正确拒答数 / 全部不可回答题数；同步报告可回答题误拒答率 | 为什么要有它：全部拒答不能成为最优策略 |
| 分层效果 | 精确标识、语义改写、多证据关联、证据不足分别报告；固定 BM25 对比混合检索，代码侧另比较 rg/live 等实际策略 | 为什么要有它：平均值会掩盖某一类问题退化，也不能偷换两套检索默认值 |

### 4.3 治理、恢复、资源与追踪

| 指标 | 统计口径 | 为什么要有它 |
| --- | --- | --- |
| 合法操作误拒绝 | 明确应允许、规格可见且具备验收前提的对照中，被平台规则错误拒绝的数 / 实际执行的应允许对照数；附拒绝规则与正确性核对。模型未修好、真实缺权和环境缺失分别记录 | 为什么要有它：边界机制既要拦越界，也要让合法任务完成；不能把所有未交付都算平台误拒 |
| 错误放行 | 出现未经授权写入/越界副作用或错误接受过期绑定的注入运行数 / 预定应拒绝的注入运行数；记录拒绝前是否已产生副作用 | 为什么要有它：返回 blocked 之前先写了源码，仍是错误放行 |
| 恢复成功率 | 中断后在原任务身份和累计预算内达到预定终态且无重复副作用的运行数 / 预注册可恢复注入运行数 | 为什么要有它：重新开始整项任务或多执行一次 Apply 不等于正确恢复 |
| 重复副作用 | 发生重复持久操作的运行数 / 重试或恢复测试运行数，附额外副作用事件数；进程/文件/执行收据共同核验 | 为什么要有它：仅看最终内容相同可能遗漏执行了两次的行为 |
| Token 与调用 | 全链各阶段及续接的实际输入/输出/缓存 Token、模型请求数、工具调用数；失败和重试全纳入；估算与 provider usage 分栏 | 为什么要有它：只量最后一轮或把字符数当真实 Token，会夸大优化 |
| 每成功任务成本 | 该臂全部预注册运行的实际成本合计 / 成功任务运行数；货币、计算时长、人工时间分别列，成功数为 0 时 N/A | 为什么要有它：不能把失败消耗丢掉，也不能把本地推理说成零成本 |
| 耗时 | 任务受理到最终验收的端到端墙钟、主动计算、人工等待分开；明确所选段/完整任务及成功/失败范围，报告逐次耗时、中位数/范围和nearest-rank P95=排序后第ceil(0.95n)个值 | 为什么要有它：审批等待与推理速度含义不同，快速失败和小样本最大值都不能冒充稳定交付提速 |
| 资源收益 | 同任务配对比较全任务输入 Token、平均工具调用、P95，并同时列完成率差和用量记录覆盖率 | 为什么要有它：少做事导致便宜不能被当成质量不变的优化 |
| 可完整重建率 | 失败样本中能按身份重建请求、实际模型 I/O、工具观察、源码/补丁、批准、验收与续接关系的样本数 / 预注册失败样本数；不适用阶段有明确依据 | 为什么要有它：缺了首次失败输入的漂亮 Trace 图仍不能完整重建 |
| 故障定位时间 | 从审阅者获得材料到提交且经独立核对正确的首因定位；基础日志 vs 完整 trace 使用相同失败样本、盲化材料和不同/交叉平衡审阅者 | 为什么要有它：同一个人第二次看同一故障会因记住答案而更快 |

耗时超时保留为超时/删失项，报告达到的时间下界和超时数；不得从 P95 分母静默剔除。定位错误和定位超时单列，不能当“很快定位成功”。为什么要有它：只保留完成的快速样本会夸大性能和诊断收益。

产品推理、专项实验与平台研发的成本分栏；一次测量引用同一运行不重复计费。Token不能直接冒充金额或人工节省；本地计算/人工成本按实际可得记录核算。为什么要有它：局部调用便宜或保存方案续接零调用，并不能证明整体经济性。

### 4.4 Self-RAG 研究项

该项单独立项：先证明需要改进的无证据断言问题，再准备 Critic 标注/复核、训练筛选、反思 token 数据与训练/重载证据；对固定检索、外部质量评估、训练后的策略使用相同独立样本及可比较预算。无证据断言率 = 缺乏有效证据支持的可核验事实数 / 全部可核验事实数，同时报告任务效用、引用覆盖、拒答、额外调用、延迟与训练计算成本。为什么要有它：普通反馈循环和 Patch SFT 不能替代训练型 Self-RAG 的实现及效果证据。

实现、训练/重载成功与质量收益分开回填；当前已有真实训练及负面质量对照，按[成果清单](PROJECT_OUTCOMES.md)引用。后续若检验Critic价值，除固定检索外增加相同生成器的“直接重写一次”对照；先核标签、协议或决策的具体失效，不因已有训练而无假设扩量。为什么要有它：训练已完成的事实应保留，同时区分判断器价值与多一次生成的效果，不让研究成为所有交付的前置条件。

下列是记录清单，不是新建的运行时 JSON Schema。已有同义字段通过映射复用，补充评测字段只引用原产物，不重写原 run。为什么要有它：统一统计口径无需另起 ArtifactStore 或给旧合同偷偷增加字段。

| 记录 | 必要信息 | 为什么要有它 |

## 6. 分层验证与成果回填

| 层级 | 计划采用的门禁 | 当前状态 | 为什么要有它 |
| --- | --- | --- | --- |
| 日常开发 | 改动对应反例与直接调用者检查、格式/契约检查；无需每次跑无关全集 | 当前已有部分工程选集；具体覆盖以执行结果为准 | 为什么要有它：反馈应足够快且直接检验改动 |
| 候选迭代 | 开发/验证集行为结果、保留行为、用量完整性；治理检查中错误放行与重复副作用均为 0 | 本协议设计，未新增 CI 自动执行 | 为什么要有它：交付收益不能掩盖已观察到的边界失败 |
| 正式评测与成果声明 | 版本冻结、独立审阅、预注册留出批次、原始证据和指标齐全；缺项明确阻断对应成果声明 | 尚未形成真实全链自动门禁 | 为什么要有它：测试存在与发布必检是两件事 |

质量改进的采用标准在运行前登记；效率改进至少要求配对任务成功数不降、必要保留行为无新增失败、错误放行/重复副作用为 0，再判断成本指标是否下降。探索小样本不足以支持普遍优于基线的声明；当前功能的采用与交付按适用验收和执行边界判断。正式效果声明的阈值与不确定性要求事先确定。为什么要有它：防止跑完后降低质量要求，或把偶然的小样本变化推广为通用收益。

下一交付周期的最低能力证据拟定为：新增非配置任务经正常入口完整交付；出现实际行为失败后，产品模型产生有效修订并通过全部原适用验收；受影响的已成功任务没有新增回归，且边界检查成立。两种能力可由同一真实任务展示，但跨工程迁移和重复可靠性仍需其对应任务集。该里程碑不是通用商用门槛，也不宣称本项目已经达到。为什么要有它：先让交付和修订能力出现可核验的实质变化，再谈整体成功率，而不是只提高局部检查分数。

## 7. 参考其他Coding Agent的评测方法

2026-09-29查阅以下一手资料；采用其测量思想，不搬用榜单成绩、样本难度或调用额度作为本项目标准。为什么要有它：不同模型、工具、任务与交付边界下的百分比不能直接比较。

| 来源 | 参考点 | 本项目应用与边界 |
| --- | --- | --- |
| [SWE-bench评分实现](https://www.swebench.com/SWE-bench/api/harness/)；[SWE-agent批量评测](https://swe-agent.com/latest/usage/batch_mode/) | 缺陷检查修复且既有行为保持；补丁生成与执行评分分开 | 采用需求/保留行为双检查，本项目交付还核对应任务的Apply、Build、Runtime范围；空组不自动宣称已验证 |
| [Aider代码编辑基准方法](https://aider.chat/docs/benchmarks.html) | 历史方法同时报告首次提交及反馈后的结果，也关注编辑协议是否能正确落盘 | 区分首稿、格式恢复和行为修订；不照搬其旧模型成绩、固定两次机会或截断错误输出方式 |
| [OpenHands结果格式](https://github.com/OpenHands/openhands-index-results) | 逐实例保留resolved、成本、版本等信息；未知值保留null | 复用已有逐任务原件和汇总，将代码就绪、交付、自主性及统计覆盖分别表达 |
| [Anthropic Agent评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 检查实际终态，区分能力与回归、单次成功与重复可靠性，核查裁判公平性 | 首先验收结果，针对失败读轨迹；不要求固定推理/工具顺序，不从“至少成功一次”推导稳定可用 |

【待测】仅由可复核真实运行回填；工程检查只填写检查范围，准备任务只填写准备数量，诊断题只填写该语料范围结果，0 新增模型调用只填写对应审批续接。结果没有改善时保留基线与负面结论。为什么要有它：简历成果必须与执行层级对应，不能由架构描述或计划数量推导。
