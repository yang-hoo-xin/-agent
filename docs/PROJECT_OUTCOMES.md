## 成功数据怎样读

[EDD成功条件](EVALUATION_DRIVEN_DEVELOPMENT.md#21-单个任务的成功条件)分别定义补丁可用、任务已交付和自主程度。一次完整trial可包含预算内的多次提交和自动修订；首次trial成功不等于首次补丁就正确。下面仅重述[原冻结候选的两题三轮][E1]，不改变原评分：

| 问题 | 原样本给出的数据 | 可支持的判断 |
| --- | --- | --- |
| 首轮完整运行交付多少题？ | 1/2 | 一道题首轮交付，不能推出首个补丁通过率 |
| 哪些题曾经成功？ | 至少成功一次1/2；Catalog为1/3次，Transfer为0/3次 | 当前两个题中只有一个曾成功 |
| 哪些题每次都成功？ | 三次均成功0/2 | 没有任务达到这组三次重复的全成功条件 |
| 所有重复运行合起来怎样？ | 1/6次交付 | 运行级结果，不能写成6道独立题 |
| 首次行为失败后修好了多少？ | 三轮汇总：冻结候选0/1（cc3）；冻结基线0/2（cb2、cb3），见[逐运行行为记录][E1] | 条件分母分别为实际进入行为失败的1、2次运行，既非全部6次，也非首轮；机制比较需固定相同失败候选 |

公开开发探针3/4属于部分进展，尚未达到补丁可用；配置任务完成5项检查及Apply/Build支持其既定交付范围。原始记录关于模型来源和介入的说明保留，自主性不能仅由batch的success字段推断。为什么要有它：同一组事实回答不同问题，阶段通过、任务交付、稳定性和人工依赖应分别展示。

## 简历叙事的组织方式

当前公开名称：**RepoForge**。

项目概述候选：围绕需求修改与缺陷修复，设计并结合AI编码工具实现源码调查、补丁生成、真实验收和授权交付流程；利用任务运行记录比较完成情况、失败修订、成本及修改边界，推动平台迭代。

主叙事围绕“任务交付、受控执行、数据驱动改进”组织，技术只在解释机制和选型时出现；RAG/Self-RAG放在其已验证用途下。七项详细数据保留在此清单及原件中，简历可按岗位取其中最有支撑的3—5条。为什么要有它：减少技术名词堆叠不等于删掉测量责任，读者应先理解解决什么问题与产生什么结果。

阶段复盘和项目介绍讲清场景、约束、关键难点、技术取舍、失败案例、指标与演进路线。框架或组件要对应它解决的核心问题，并说明未选替代方案的依据；工程判断与实际对照结论分别标注。为什么要有它：技术名称不能单独说明工程价值，也不能把未做过的方案比较补写成选型成绩。

成功率、延迟、成本和数据量均能追到数据集来源与规模、独立任务数、运行次数、统计口径、版本/预算及失败样本；优先引用已有原件和定义。为什么要有它：无法复现或解释分母的数字会降低可信度，已有记录无需在每次开发中重复抄写。

这些维度在阶段总结或对外表述时检查，日常开发只更新变化的事实与决定。为什么要有它：项目叙事需要随真实成果沉淀，不能变成每个修复开始前都要填满的材料清单。

“完成率提升”“成本降低”“定位缩短”“断言率下降”均由同口径对照决定方向；当前负结果可以表述为发现退化并回退，不能填进预设的正向句式。企业节省工时、收入或生产稳定性待有实际使用数据后再写。为什么要有它：成果要经得起追问，不能由技术实现或演示推算业务回报。

## “合格”的验证对象

下一阶段按选定应用范围检查：能从需求交付完整可验收修改；出现真实失败后能产生有效修订并通过原验收；不同工程/任务类型有可复查结果与重复波动；合法操作与应拒绝操作均经过验证；成本、人工介入和失败过程能追溯。每项的任务清单、适用验收和可接受预算在对应验证前确定。为什么要有它：项目质量由可用性、可靠性、成本和边界共同支撑，测试数量或某个自选百分比不能单独证明成熟。

下一交付周期先取得新增非配置任务的完整交付和真实失败后的有效修订证据，并检查受影响的已成功行为。不同工程的新任务、重复可靠性和七项专项数据继续按其范围验证；外部榜单分数不直接充当本项目合格线。为什么要有它：给开发一个能检验产品变化的近期终点，同时保留完整项目目标。

项目至少说明质量评估、成本/延迟、安全、故障处理、可观测性与生产化边界六个方面的证据及缺口。生产化边界具体到已验证环境、部署/运行范围、依赖和维护条件，未验证部分按实际前提推进。为什么要有它：这些条件决定系统能否在目标场景中交付和维护，演示成功本身不能证明完整生产可用性。
