状态：当前产品目标与执行边界；更新于 2026-09-29。当前任务见[实施队列](IMPLEMENTATION_QUEUE.md)，能力事实见[项目状态](PROJECT_STATE.md)。

## 1. Product

项目目标是理解自然语言需求，完成新 Mod 创建、生成过程中的迭代修复，以及接手已有问题 Mod／代码库后的按需修改，经适用验收受控交付。首个验证领域是 GTFO / BepInEx Mod。LangGraph 负责工作流，ArtifactStore 负责持久业务产物与谱系；领域行为留在 domain 模块。

三种任务共用调查、生成、验证和修订能力。意图识别需要区分任务起点、目标行为、保留行为和缺失信息；继续修复使用当前候选与实际反馈，接手已有工程允许以源码编译失败为起点。各路径的实际完成情况按运行证据记录。为什么要有它：用户可能从一句想法、半成品或问题工程进入，工程不完美正是需要 Agent 的原因。

```text
自然语言与任务起点（新建／继续修复／接手已有）→ 需求与验收边界
→ 活源调查 → Evidence / Plan / Binding → Patch
→ 确定性 Review → 无写入 Dry-run → 精确批准 → 隔离 Apply
→ 实际 Build → 适用的 Runtime / Eval / Repair → 交付或明确未完成
```

### 1.1 Current Development Selection

开发方向为评测驱动迭代；具体任务由当前用户请求选择，[实施队列](IMPLEMENTATION_QUEUE.md)只作短导航。历史任务、旧额度和旧授权不自动恢复。为什么要有它：稳定产品契约不能把一次会话的选择永久变成下一次任务指令。

## 2. 执行与权限边界

| 边界 | 约束 | 原因 |
| --- | --- | --- |
| 证据与修改目标 | 修改依据当前目标源码、API 和已绑定观察；检索分数、模型建议和历史经验不授予写权限，目标由有效 Binding 限定 | 为什么要有它：相关性不等于来源当前有效，更不等于获得修改批准 |
| Review 与 Dry-run | 原确定性审阅先通过，Dry-run 展示精确变更且不写源码；可选 Critic 不替代硬检查 | 为什么要有它：评估意见不能越过真实执行约束 |
| 产品源码 Apply | 消费精确 diff/上下文授权并重新核验活源；沿用有效人审，或消费明确任务委托策略。当前策略分支限已授权的可丢弃隔离目录、compile-only、通过绑定验收的变更；记录真实授权来源 | 为什么要有它：授权须对应当前版本与副作用，避免重复审批，同时防止模型自授权限或将策略授权冒充人审 |
| 外发与凭据 | 外部模型收到的数据类别、目的地和运行范围须在有效授权内；密钥不进入产物、日志或可见摘要 | 为什么要有它：一次外发授权不能推导出其他数据或目的地的许可 |
| Build / Runtime | Build 成功要求真实命令成功及目标产物核验；游戏启动、目录复制和玩法观察各按适用授权执行 | 为什么要有它：供应的输出、编译成功和实际游戏行为是不同事实 |
| 验收与续接 | 实现前说明验收和 Build/Runtime/Eval 的适用性；必需项未证实就保留未完成；续接保留谱系、原始结果及累计预算 | 为什么要有它：成功不能来自跳过失败阶段、重领预算或覆盖历史 |

以上是产品执行边界。用户要求的平台开发、文档维护和局部修复按 [AGENTS.md](../AGENTS.md) 与实际权限推进，不套用产品源码 Apply 的审批流程。为什么要有它：开发助手的实现工作和产品 Agent 对目标工程的执行是不同权限对象。

## 3. 验证与成果口径

| 证据 | 能支持的结论 |
| --- | --- |
| 源码/调用链检查 | 存在相应实现或接线；未证明运行正确 |
| 当前版本聚焦测试 | 所覆盖的行为在该测试环境通过 |
| Dry-run | 指定前像匹配、精确 diff 可审阅且没有源码写入 |
| 已批准隔离 Apply | 获准字节已写入指定隔离目标 |
| 真实 Build 与产物身份 | 该目标构建成功；没有推出 Runtime 通过 |
| 绑定到当次运行的行为观察 | 对应验收条件在该环境的实际结果 |
| 独立任务对照 | 冻结任务、模型、预算及判定范围内的效果与成本 |

报告采用与证据相符的最窄结论，缺失记 unknown；旧测试或单个 Mod 结果不能自动升级为当前版本、多项目或通用效果。为什么要有它：可运行模块、工程通过和独立任务成功支撑不同主张。

## 4. 检索与任务选择

当前产品源码入口默认 `rg_live`，可选 `indexed_source`；文档 RAG 的 BM25/Dense 对照另见[复用审计](audits/EVALUATION_REUSE_AUDIT_20260926.md)。两种范围分别判断，不以文档问答结果决定代码修改权限。为什么要有它：检索对象、验收标准和权威来源不同。

新工作来自用户需求、已观察失败或具体产品决策；先核已有入口、配置、工厂、实现及验收，再比较复用与新增的改动成本。规则、评测、检索或训练模块的存在本身不创建新任务。为什么要有它：避免漏查已有能力，也避免为旧路线图或模块数量投入无效工作。

本文件保留稳定产品边界；具体实现以活源为准，开发约定以 [AGENTS.md](../AGENTS.md) 为准。文档冲突按当前请求和实际约束纠正，不把无关旧叙述变成全面停工条件。为什么要有它：过期文档应被维护，不能反过来覆盖当前授权或真实代码。
