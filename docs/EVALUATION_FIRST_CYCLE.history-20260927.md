# 首轮评测驱动开发计划

日期：2026-09-26。状态：真实本地模型开发基线、RAG 对照和治理测试已执行；当前继续修复实际入口与测量缺口。已执行范围以[首轮结果](audits/EVALUATION_FIRST_RESULTS_20260926.md)及其原始证据为准，下面尚未执行的题数与重复数仍是候选。

用户已追加要求实际测量、完成缺失前提，并明确沿用现有本地模型建立可复现基线。指标定义见[评测驱动开发协议](EVALUATION_DRIVEN_DEVELOPMENT.md)。当前执行选择见[实施队列](IMPLEMENTATION_QUEUE.md)，每项实验的确切模型、预算、输入和暴露状态由执行前协议保存。

## 1. 首轮问题与基线

首轮选择已有 verifier 能验收的真实开发任务跑正常入口，随运行收集必要的输入、用量、终态和交付回执；遇到缺失时补齐受影响的记录或接线。第二项及后续数量按用户目标、暴露状态和实际缺口决定。为什么要有它：仓库已有执行器和验收注入点，实际任务能暴露最小缺口，无需先完成全部字段与续接的覆盖审计。

| 角色 | 首轮选择 | 为什么要有它 |
| --- | --- | --- |
| B0 当前产品基线 | 冻结当前可执行工作区；HEAD 为 `3381143790b52b0be7fa8ba32b59f5d10fa6a89a`，但有大量 tracked/untracked WIP，尚未生成完整执行快照 | 为什么要有它：HEAD 相同不代表实际代码相同，不能以它单独绑定基线 |
| B1 下一候选 | 根据 B0 的真实失败完成所需的相关修复；资源优化按已观察瓶颈选择，因果收益另设单因素对照 | 为什么要有它：完整解决工程问题与隔离统计因果不同，开发改动不必人为拆成多次失败运行 |
| 后续结构对照 | 简单 `rg/live read + 同模型修订` 与完整 Graph 仅在真实适配、反馈对称和统一裁判就绪后运行 | 为什么要有它：现有 controlled adapter 不能直接当作已具备真实双臂执行能力 |
| 后续资源对照 | 观察复用、上下文重组或 memory on/off 一次只选一项；全阶段消费原始 usage | 为什么要有它：同时改多个因素无法判断节省来源，阶段字节数也不能代替全任务 Token |

## 2. 实施顺序和退出条件

下面数量是规划值，不是已有样本或已执行结果；节奏随验收完成推进，不承诺日历天数。

| 阶段 | 工作与交付物 | 完成条件 | 为什么要有它 |
| --- | --- | --- | --- |
| E0 本轮 | 流程、指标字典、任务卡和本计划；活动文档链接同步 | 文档链接、现有入口名称和改动范围检查通过 | 为什么要有它：先建立一致口径，不在未知模型与预算下启动实验 |
| E0a 本轮已检查 | 源码/调用者扫描、8 个冷进程 help、历史 RAG 聚合复核、真实历史 Trace 只读投影 | 结果与局限见唯一复用审计 | 为什么要有它：把模块存在、接线与实际可运行区分开 |
| E0b 下一候选 | 用一条既有真实任务历史做实验结果行映射；复用 Trace/执行索引/交付收据，核全续接与缺失字段；比较扩旧模块和新薄投影 | 输出字段来源表及最小修改范围，不运行新模型；旧 comparator 的单题/no-write 和新交付口径不混用 | 为什么要有它：先用已有事实测出集成代价，再决定复用或新做 |
| E1 基线准备 | 先选已有 verifier 适用的一项真实开发需求；配置修改、API 缺陷等旧题可作开发回归，第二题按缺口选择；记录来源/验收/依赖/暴露 | 有可执行验收，冻结 B0、模型/预算/权限、记录方案与独立审阅方式 | 为什么要有它：任务优先匹配可验证的真实能力，不为凑题数重造已有裁判 |
| E2 首个闭环 | 已选任务各 1 次 B0；保留所有终态；从首个可复现工程失败选一项修复，定点检查后同输入执行 B1 | 两臂结果表及原始证据齐全；如基线执行阻断，交付准确阻断与最小修复，不伪造对照 | 为什么要有它：先证明可测、可修、可复核，避免带缺陷重复长跑 |
| E3 稳定性与治理 | 修复后的候选在开发/验证题做预注册重复；执行下表 8 类异常注入 | 建议每题每臂 3 次，包含 E2 首次且仅当身份/协议未变；治理观察与计数齐全 | 为什么要有它：检测偶发失败和续接副作用，已有不同版本运行不能拼成重复实验 |
| E4 小型独立验收 | 规模候选之一为 12 项任务：4 development、4 validation、4 holdout，E1 已选样本包含在 development；最终数量按任务资格决定，按家族隔离 | 候选冻结后评测方执行 holdout 的预注册批次并给出独立判定；看过失败后进入回归，不再用于下一轮独立宣称 | 为什么要有它：先形成三分集机制，4 道留出仅能给探索性计数，不能支持稳定泛化结论 |
| E5 按缺口扩展 | 当跨项目/语言适配与验收可用，扩展真实项目、家族和独立任务；从同批失败挑诊断样本，另做检索与资源配对 | 实际执行多少就报告多少；用新增独立任务积累成果，不通过增加重复或参数变体充数 | 为什么要有它：扩规模应检验新的能力范围，而不是美化样本数 |

每臂每运行预算在 E1 记录确切值：全任务与阶段模型调用上限、输入/输出 Token 上限、工具轮数、墙钟上限、货币上限或本地计算时间。运行规模按已选任务数 × 臂数 × 重复数计算，模型调用上界再乘单运行预算；例如后续确实选定 2 题/2 臂/3 次才是 12 次任务运行。为什么要有它：任务运行数不是模型请求数，规模例子也不是已冻结分母。

E4 优先验证同项目新家族，不要求首轮同时凑齐 Python 与 C#；Python fixture 不计真实 Python 工程交付。目标项无法取得合适任务时记录覆盖缺口。为什么要有它：语言清单应该来自真实修改和验收，不能来自评测脚本的编写语言。

## 3. 八类治理与恢复场景

在隔离测试目标上通过真实公开入口注入；替身测试与真实进程/文件验证分栏。每例记录初始源码、批准绑定、注入时点、返回状态和实际副作用。为什么要有它：返回码或单测通过不足以证明真实写入和中断边界。

| ID | 场景 | 预定判定；分母类别 | 为什么要有它 |
| --- | --- | --- | --- |
| G01 | 批准后、Apply 前源码漂移 | 拒绝旧批准；无目标写入；应拒绝 | 为什么要有它：批准不能覆盖已变化的前像 |
| G02 | 提交含越界文件或路径逃逸 | 拒绝且边界外零写入；应拒绝 | 为什么要有它：允许生成的内容仍须服从精确修改范围 |
| G03 | 相同操作重复提交或并发续接 | 恰好一次持久副作用，其余复用收据/拒绝；重试副作用 | 为什么要有它：响应丢失或双击不能造成重复执行 |
| G04 | Apply 前终止进程再续接 | 沿原身份和预算完成一次合法 Apply；可恢复、重试副作用 | 为什么要有它：恢复不能绕过原批准或重新领取预算 |
| G05 | Apply 已生效、回执返回前终止 | 识别既有写入并对账；无第二次 Apply；可恢复、重试副作用 | 为什么要有它：最危险的重复发生在动作已完成而调用者未知时 |
| G06 | Build 失败后重启并查询/合法续接 | 保留真实 Build 失败、原产物及预算，不误报 delivered；以该可查询失败态为本例恢复终态；可恢复、重试副作用 | 为什么要有它：状态恢复成功与 Build 修复成功是不同指标 |
| G07 | 跨任务/跨 diff 复用批准 | 拒绝且不执行；应拒绝 | 为什么要有它：批准属于特定变更，不能变成全局写许可 |
| G08 | 预算耗尽后重启/续接 | 保持耗尽并拒绝新增受限调用；应拒绝 | 为什么要有它：累计预算须跨进程延续，正确恢复并不总意味着继续执行 |

上述是 8 类设计，不是 8 个已执行案例。每类可有多个预注册注入点/重复；错误放行、恢复和副作用各使用自己的适用分母，不能统一除以 8。为什么要有它：并非每个异常都应拒绝或可恢复，混用分母会误导治理结论。

## 4. 其他【待测】如何进入后续开发

| 成果方向 | 最早可复用的真实活动 | 首次可回填条件 | 为什么要有它 |
| --- | --- | --- | --- |
| 端到端与持续迭代 | E2 开发闭环、E4 留出批次 | 按协议分别给开发/独立任务数、成功数、波动与检查范围 | 为什么要有它：开发题成功和未参与调优的成功不能合并 |
| RAG 选型 | 旧诊断报告已溯源复核；先解释其测量缺失和固定 router 边界，再决定新增语料/独立题 | 原始请求计数、相同计时边界、Recall/引用/拒答及分母齐全；历史详情见复用审计 | 为什么要有它：复用已有实测可以避免重复同样实验，但不消除旧小语料和部分测量的局限 |
| 治理恢复 | E3 八类场景 | 真实拒绝/续接收据及副作用前后核验 | 为什么要有它：设计了异常场景不等于经受了异常 |
| 上下文与资源 | E2/E3 全链 usage 采集后做单因素配对 | 同任务集用量覆盖、完成率变化、P95 及未知项齐全 | 为什么要有它：缺失用量时先补观察，不先宣布节省 |
| 追踪定位 | 首轮自然失败；不足时另列人工注入样本 | 重建清单和盲化诊断计时、正确性、超时记录；建议从 4–6 个不同失败开始探索 | 为什么要有它：真实失败与人工注入代表性不同，少量样本不宜宣称稳定提速 |
| Self-RAG | 主线观察到证据支持度缺陷后，独立研究立项 | 标注、筛选、反思 token 训练/重载、独立对照与额外成本证据齐全 | 为什么要有它：训练不能为了简历条目而替代更有收益的产品修复 |

## 5. 当前下一步与状态

下一候选为 E0b 的只读字段/接缝映射，不是先建设新 runner。通过映射比较复用与新增薄汇总的代价后，再推进 E1 的任务和模型选择。正式实验前补齐准确模型配置、执行快照、任务预算、目标项目与适用授权，沿用仍有效的批准。为什么要有它：先消除“仓库其实已经有”的不确定性；只有实际绑定范围变化才需要新的执行决定。

本轮未启动模型实验、目标工程 Apply/Build、训练或 CI 修改；没有新增成功率、成本节省或治理实测数字。真实阶段评测与行为裁判已有实现；待检验的是独立双臂装配、完整任务统计和具体场景接缝，不能把它们概括成全仓缺少真实执行能力。
